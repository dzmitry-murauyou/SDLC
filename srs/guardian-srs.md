## 1. Введение {#1-introduction}

Этот документ задаёт требования к Guardian — приложению для безопасного управления паролями и связанными секретами. Он фиксирует целевые возможности, границы первой версии, ограничения, качественные характеристики и способы проверки; не предписывает внутреннюю архитектуру, за исключением явно заданного требования использовать Java. Документ предназначен для владельца продукта, разработчиков, тестировщиков и специалистов по безопасности. Подтверждённые решения и оставшиеся допущения разделены в разделах 2.5 и 5.1.

### 1.1 Назначение документа {#11-document-purpose}

SRS определяет, **что** должен делать Guardian и по каким критериям принимается результат. Владелец продукта использует документ для согласования объёма; разработчики — для проектирования и реализации; QA и специалисты по безопасности — для подготовки проверок и анализа рисков. Архитектурные решения и конкретные криптографические параметры должны быть зафиксированы отдельно и не считаются определёнными этим документом.

Документ выступает главным ориентиром для всех участников проекта, определяя зоны их ответственности:
Команда разработки – использует спецификацию как основу для декомпозиции задач и реализации функциональности;
Инженеры по тестированию – опираются на требования при составлении тест-планов и критериев приёмки;
Заказчик – сверяет по документу, насколько итоговый продукт закрывает его бизнес-потребности;
Преподаватель – проводит оценку качества проектирования и проверку артефактов на протяжении жизненного цикла продукта.

### 1.2 Область применения продукта {#12-product-scope}

Guardian (релиз 1.0) — настольный менеджер паролей для Windows 10 и новее. Он позволяет создавать и хранить зашифрованные записи с логинами, паролями, адресами сайтов, заметками и TOTP-секретами, организовывать их по категориям, искать, генерировать пароли и выполнять автозаполнение в поддерживаемых браузерах Windows. Разблокировка хранилища требует мастер-пароль и зарегистрированный USB-ключ безопасности FIDO2/WebAuthn; приложение также генерирует TOTP-коды для внешних сервисов. Для восстановления и переноса между экземплярами Guardian пользователь создаёт зашифрованный файл резервной копии и самостоятельно сохраняет его, в том числе на внешний накопитель; облачная синхронизация и аккаунт Guardian не используются. Приложение реализуется на Java без установленного владельцем продукта требования к конкретной версии JDK.

**Входит в объём:** Windows desktop-приложение; локальное зашифрованное хранилище; обязательная двухфакторная разблокировка; записи паролей, заметок и TOTP-секретов; категории, поиск и генератор паролей; автозаполнение в утверждённых браузерах Windows; экспорт и восстановление зашифрованной резервной копии Guardian для переноса между экземплярами и хранения на съёмном носителе.

**Не входит в объём релиза 1.0:** мобильные приложения и приложения для других ОС, аккаунт Guardian, облачная или автоматическая синхронизация, совместное/корпоративное хранилище, импорт из сторонних менеджеров и незашифрованный экспорт в универсальные форматы, восстановление секретов оператором и функции ИИ. Конкретные поддерживаемые версии Windows и браузеры для автозаполнения фиксируются в платформенной матрице до релиза.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

Guardian — Windows desktop-приложение для индивидуального пользователя, предназначенное для Windows 10 и новее, заменяющее хранение паролей в заметках, браузерных формах и таблицах. Оно хранит данные локально и взаимодействует с Windows и поддерживаемыми браузерами только для автозаполнения, буфера обмена, диалогов файлов и блокировки сессии. Сетевого аккаунта и сервиса синхронизации нет: перенос осуществляется пользователем через зашифрованный файл Guardian. Владелец продукта и поддержка должны быть назначены до выпуска; для автономного приложения сетевой SLA неприменим, а поддержка не получает доступа к секретам.

```text
Пользователь ──> Guardian (интерфейс, зашифрованное хранилище, генератор, TOTP)
                         │
                         └──> Поддерживаемый браузер/приложение (только при автозаполнении)
```

### 2.2 Функции продукта {#22-product-functions}

- Создание, двухфакторная разблокировка, блокировка и удаление личного хранилища.
- Добавление, просмотр, изменение и удаление записей с учётными данными и заметками.
- Организация записей по пользовательским категориям и поиск по разрешённым метаданным.
- Генерация случайных паролей по выбранным пользователем параметрам.
- Автозаполнение учётных данных в поддерживаемых средах с проверкой соответствия источника записи.
- Сохранение TOTP-секретов и показ актуальных одноразовых кодов.
- Защита от случайного раскрытия: скрытие секретов, автоматическая блокировка и очистка буфера обмена.
- Создание зашифрованного файла резервной копии и восстановление/перенос данных между экземплярами Guardian; пользователь может сохранить файл на внешний накопитель.

### 2.3 Ограничения продукта {#23-product-constraints}

| ID | Ограничение |
|---|---|
| CON-01 | Guardian должен быть настольным приложением для Windows 10 и новее; мобильные версии и отдельные приложения для других ОС не входят в релиз 1.0. |
| CON-02 | Прикладная логика должна быть реализована на Java. Владелец продукта не задаёт конкретную версию Java/JDK; команда выбирает поддерживаемый выпуск и фиксирует его до сборки релиза. |
| CON-03 | Секретные поля локального хранилища и резервные файлы должны быть зашифрованы; мастер-пароль, ключ и фактор аутентификации Guardian не должны сохраняться в открытом виде. Резервная копия защищается паролем Guardian (мастер-паролем), отдельный пароль копии не требуется; дополнительный слой шифрования может быть рассмотрен в проектном решении. |
| CON-04 | Вход в Guardian должен требовать мастер-пароль и USB-ключ безопасности, совместимый с FIDO2/WebAuthn; TOTP-секреты для внешних сервисов являются отдельной функцией. |
| CON-05 | Версия 1.0 не должна иметь аккаунт Guardian, облачное хранилище или автоматическую синхронизацию; передача данных между экземплярами выполняется вручную через зашифрованный файл Guardian. |
| CON-06 | Импорт/экспорт должен поддерживать только формат резервной копии Guardian; экспорт паролей в открытые универсальные форматы и импорт из сторонних менеджеров не входят в релиз. |
| CON-07 | Интерфейс и пользовательская документация релиза 1.0 должны быть на русском языке; другие локализации не требуются. |
| CON-08 | Конкретные криптографические алгоритмы и параметры должны быть выбраны и обоснованы в проектной документации с использованием проверенных библиотек; самописная криптография запрещена без отдельного утверждённого исключения. |
| CON-09 | Юрисдикция, применимые законодательные требования и лицензирование должны быть определены до публичного выпуска. |
| CON-10 | Численные цели производительности и интервал автоматической блокировки не являются критериями приёмки релиза 1.0; они могут быть определены позднее по результатам эксплуатации. |

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Класс пользователей | Навыки, частота использования и цели | Доступ и потребности |
|---|---|---|
| Владелец хранилища | Обычный пользователь без обязательных знаний о криптографии; использует Guardian ежедневно или несколько раз в неделю, чтобы создавать, находить и применять секреты. | Полный доступ к собственному хранилищу после разблокировки; понятные сообщения об ошибках и доступная навигация с клавиатуры. |
| Пользователь автозаполнения | Часто входит на сайты/в приложения, обычно несколько раз в день; ожидает быстро выбрать подходящую запись и проверить целевой источник. | Может выбирать только записи своего хранилища; раскрытие и передача секрета требуют явного действия. |
| Специалист поддержки/разработчик | Использует инструменты диагностики по мере необходимости при обращениях и сопровождении релиза. | Штатного доступа к пользовательским секретам нет; получает только очищенные диагностические данные с согласия пользователя. |

Интерфейс и пользовательская документация релиза 1.0 должны быть только на русском языке. Guardian работает в Windows 10 и новее; интерфейс должен поддерживать стандартное управление клавиатурой, масштабирование Windows и системные настройки доступности. Требования к соответствию конкретному стандарту доступности подлежат подтверждению до релиза.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

| A-02 | Пользователь должен хранить мастер-пароль и запасной USB-ключ или иные утверждённые данные восстановления в безопасном месте. | Владелец продукта / UX (назначить) | Утрата мастер-пароля или единственного доступного ключа восстановления может лишить пользователя доступа. | Предупреждать пользователя при создании хранилища и резервной копии; не обещать операторское восстановление. |
| A-03 | Устройство работает под Windows 10 или новее в конфигурации из утверждённой матрицы и не скомпрометировано. | Пользователь; команда безопасности отвечает за описание модели угроз | Защита от вредоносного ПО, кейлоггеров и физического доступа к разблокированному устройству не гарантируется. | Документировать границы гарантий; проводить анализ угроз; блокировать хранилище при блокировке/выходе из Windows. |
| A-04 | Для автозаполнения будут выбраны поддерживаемые браузеры Windows и проверен механизм интеграции настольного приложения с ними. | Владелец продукта / техлид (назначить) | Нельзя завершить тесты автозаполнения и подтвердить безопасную привязку домена. | До релиза утвердить матрицу браузеров; неподдерживаемые браузеры явно исключить. |
| A-05 | Поддерживаемые Java-библиотеки криптографии, TOTP и генерации случайных чисел доступны и проходят проверку безопасности и лицензий. | Техлид / специалист безопасности (назначить) | Придётся менять библиотеки или целевую Java-среду; самописная криптография создаёт неприемлемый риск. | Выбрать и проверить библиотеки на PoC; зафиксировать Java/JDK перед сборкой. |

Возможность дополнительного слоя шифрования требует решения. | Команда проекта / специалист безопасности | Потеря мастер-пароля может сделать копию недоступной; дополнительный слой может усложнить восстановление. | Не хранить пароль в файле; утвердить криптографическую схему и UX восстановления до реализации. |

## 3. Требования {#3-requirements}

Требования должны быть проверяемыми, однозначными и иметь уникальные идентификаторы. Формулировки «должен» и «не должен» обязательны для релиза 1.0, если требование не помечено как ожидающее согласования. Численные цели производительности и интервал бездействия до автоматической блокировки не входят в критерии приёмки релиза 1.0 (CON-10).

📃 Шаблон требования:

- **ID:** REQ-FUNC-EXAMPLE
- **Title:** краткий заголовок требования
- **Statement:** система должна…
- **Rationale:** обоснование
- **Acceptance Criteria:** критерии приёмки
- **Verification Method:** Test | Analysis | Inspection | Demonstration | Other
- **More Information:** дополнительный контекст или ссылки

**Схема идентификаторов:** `REQ-[AREA]-[NNN]-[VER]`, где `-[VER]` необязателен; идентификаторы уникальны и неизменяемы. Изменения требований отражаются в истории документа. Каждый тестовый артефакт должен ссылаться на ID соответствующего требования.

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

Интерфейс должен предоставлять отдельные представления для списка записей, категорий, поиска, редактирования записи, генератора, настройки TOTP и резервного копирования; ручное редактирование файлов не требуется. Секреты скрыты по умолчанию, а раскрытие и копирование требуют явного действия. Интерфейс должен поддерживать состояния пустого хранилища, отсутствующих результатов, ошибки разблокировки, ошибки сохранения, неподдерживаемого источника автозаполнения и повреждённой копии; сообщения не должны показывать секретные значения. Интерфейс релиза 1.0 предназначен для Windows 10 и новее; клавиатурная навигация, масштабирование Windows и системные средства доступности должны быть проверены в UX-спецификации.

Графические материалы (PNG-макет и исходная модель SysML v2) приведены в приложении.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

Guardian должен поддерживать взаимодействие с USB-ключом безопасности FIDO2/WebAuthn для разблокировки. Установка должна работать на Windows 10 и новее с совместимым Java runtime, выбранным командой. Иные специализированные устройства и биометрические датчики не требуются.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

- Взаимодействие с браузерами Windows для автозаполнения разрешено только через поддерживаемый и документированный интерфейс интеграции.
- Формат записи должен поддерживать название, логин, пароль, URL/идентификатор источника, категории, заметки и необязательные TOTP-данные.
- Внешний сетевой API, облачная синхронизация и сторонние аналитические SDK не входят в объём версии 1.0.


- **ID:** REQ-INT-001
- **Название:** Интерфейс управления секретами
- **Утверждение:** Пользовательский интерфейс должен скрывать секретные значения по умолчанию и требовать явного действия пользователя для раскрытия, копирования или автозаполнения секрета.
- **Обоснование:** Предотвращает случайное раскрытие данных при обычной навигации.
- **Критерии приёмки:** Пароли и TOTP-секреты не отображаются в списке записей; раскрытие/копирование инициируется отдельным действием; ошибки интерфейса не содержат значений секретов.
- **Метод проверки:** Инспекция, функциональный тест.
- **Дополнительная информация:** CON-07; связано с: REQ-SEC-002.


- **ID:** REQ-INT-002
- **Название:** Ограничение внешних интеграций
- **Утверждение:** В релизе 1.0 система не должна передавать данные хранилища внешним сетевым сервисам; локальная интеграция с Windows и браузером допускается только для документированных функций. Передача секрета браузеру разрешена исключительно в явно инициированном пользователем автозаполнении.
- **Обоснование:** Сохраняет локальный характер продукта и ограничивает поверхность утечки.
- **Критерии приёмки:** Анализ сетевого трафика не обнаруживает исходящих запросов с данными хранилища; локальные вызовы Windows ограничены документированными сценариями выбора файла, буфера обмена, блокировки сеанса и автозаполнения; браузер получает только выбранные пользователем поля в подтверждённом целевом контексте.
- **Метод проверки:** Анализ трафика, инспекция.
- **Дополнительная информация:** CON-05; связано с: REQ-AVAIL-001.


- **ID:** REQ-INT-003
- **Название:** Безопасная интеграция автозаполнения
- **Утверждение:** Интеграция с выбранным браузером или ОС должна передавать только поля выбранной пользователем записи в явно подтверждённый целевой контекст.
- **Обоснование:** Ограничивает объём данных, доступных внешнему приложению.
- **Критерии приёмки:** Интеграционный тест подтверждает передачу только выбранных полей и отказ для неподдерживаемого или несоответствующего контекста.
- **Метод проверки:** Интеграционный тест, демонстрация.
- **Дополнительная информация:** CON-01, A-04; связано с: REQ-FUNC-006, REQ-SEC-005.

### 3.2 Функциональные требования {#32-functional}


- **ID:** REQ-FUNC-001
- **Название:** Создание и разблокировка хранилища
- **Утверждение:** Система должна позволять пользователю создать хранилище, задать мастер-пароль и разблокировать хранилище только после проверки мастер-пароля и зарегистрированного USB-ключа безопасности FIDO2/WebAuthn.
- **Обоснование:** Мастер-пароль является основным пользовательским способом доступа к данным.
- **Критерии приёмки:** При корректном мастер-пароле и втором факторе записи доступны; если любой фактор неверен, секретные поля не раскрываются и приложение показывает нейтральное сообщение об ошибке; мастер-пароль не сохраняется в открытом виде.
- **Метод проверки:** Тест, анализ.
- **Дополнительная информация:** CON-03, CON-04; связано с: REQ-SEC-001, REQ-SEC-002, REQ-FUNC-010.


- **ID:** REQ-FUNC-002
- **Название:** Управление записями
- **Утверждение:** Система должна позволять добавлять, просматривать, редактировать и удалять запись, содержащую название, логин, пароль, URL или иной идентификатор источника и пользовательские дополнительные поля.
- **Обоснование:** Это базовый сценарий менеджера паролей.
- **Критерии приёмки:** После сохранения изменения переживают закрытие и повторное открытие приложения; удалённая запись не отображается в обычном списке; ошибки сохранения не должны приводить к частичной или незаметной потере данных.
- **Метод проверки:** Функциональный тест.
- **Дополнительная информация:** CON-03; связано с: REQ-REL-001.


- **ID:** REQ-FUNC-003
- **Название:** Категории, фильтрация и поиск
- **Утверждение:** Система должна позволять назначать записи пользовательским категориям и находить записи по названию, логину, категории или адресу источника.
- **Обоснование:** Категоризация упрощает управление растущим хранилищем.
- **Критерии приёмки:** Категорию можно создать, переименовать, назначить и удалить; удаление категории не удаляет записи; результаты поиска соответствуют введённому запросу и не раскрывают пароли в результатах.
- **Метод проверки:** Функциональный тест.
- **Дополнительная информация:** CON-03.


- **ID:** REQ-FUNC-004
- **Название:** Генерация пароля
- **Утверждение:** Система должна генерировать пароль длиной от 8 до 128 символов с выбранными пользователем классами символов, используя криптографически стойкий источник случайности среды выполнения Java.
- **Обоснование:** Случайные уникальные пароли уменьшают риск угадывания и повторного использования.
- **Критерии приёмки:** Пользователь задаёт длину и включает строчные, прописные, цифровые и специальные символы; если класс выбран, результат содержит минимум один символ из этого класса; длины 8 и 128 поддерживаются, значения вне диапазона отклоняются; несовместимые настройки дают понятную ошибку; тестирование подтверждает отсутствие предсказуемого источника случайности.
- **Метод проверки:** Тест, анализ.
- **Дополнительная информация:** CON-02, CON-08; связано с: REQ-POC-001.


- **ID:** REQ-FUNC-005
- **Название:** Защищённые заметки
- **Утверждение:** Система должна позволять создавать и редактировать заметки, содержащие текст, относящийся к хранилищу, и сохранять их с той же защитой конфиденциальности, что и другие секретные данные.
- **Обоснование:** Пользователю могут потребоваться защищённые сведения, не являющиеся логином или паролем.
- **Критерии приёмки:** Заметка доступна только после разблокировки; её содержимое не появляется в журналах, поисковых подсказках внешних систем или открытых файлах хранилища.
- **Метод проверки:** Функциональный тест, инспекция.
- **Дополнительная информация:** CON-03; связано с: REQ-SEC-001, REQ-OBS-001.


- **ID:** REQ-FUNC-006
- **Название:** Безопасное автозаполнение
- **Утверждение:** Система должна предлагать автозаполнение только для записи, явно выбранной пользователем, и только при совпадении схемы, имени хоста и эффективного порта с сохранённым источником; переход на другой источник должен требовать повторной проверки.
- **Обоснование:** Автозаполнение не должно отправлять секреты на похожий или посторонний сайт.
- **Критерии приёмки:** Точный совпадающий источник допускается; похожий домен, другой порт, схема или неоднозначный URL отклоняются; поддомены не считаются совпадением автоматически; заполнение выполняется только после явного выбора пользователя и повторной проверки источника после перенаправления.
- **Метод проверки:** Тестирование интеграции и негативные тесты.
- **Дополнительная информация:** CON-01; допущение A-04; связано с: REQ-INT-003, REQ-SEC-005.


- **ID:** REQ-FUNC-007
- **Название:** TOTP-коды для сохранённых аккаунтов
- **Утверждение:** Система должна позволять пользователю добавить TOTP-секрет к записи и показывать актуальный одноразовый код, оставшееся время действия и параметры алгоритма, если они отличаются от значений по умолчанию RFC 6238.
- **Обоснование:** Пользователь запросил поддержку двухфакторной аутентификации для внешних аккаунтов.
- **Критерии приёмки:** Для тестовых векторов RFC 6238 выдаются ожидаемые коды; значения по умолчанию — 6 цифр, шаг 30 секунд и HMAC-SHA-1; поддерживаются параметры из QR/otpauth URI или ручного ввода; TOTP-секрет хранится зашифрованным и не включается в незашифрованный экспорт; оставшееся время отображается.
- **Метод проверки:** Тест, анализ.
- **Дополнительная информация:** CON-03; RFC 6238; связано с: REQ-SEC-001.


- **ID:** REQ-FUNC-008
- **Название:** Резервное копирование и перенос между экземплярами Guardian
- **Утверждение:** Система должна позволять экспортировать локальное хранилище в зашифрованный файл собственного формата Guardian и восстанавливать его в другом экземпляре Guardian после подтверждения пользователя.
- **Обоснование:** Даёт пользователю автономный способ защиты от потери данных и ручного переноса между своими экземплярами Guardian, включая хранение копии на внешнем накопителе.
- **Критерии приёмки:** Экспорт создаёт зашифрованный файл по выбранному пользователем пути, который расшифровывается паролем Guardian (мастер-паролем), без отдельного пароля резервной копии; восстановление проверенной копии возвращает записи с исходными значениями; повреждённая или неподдерживаемая копия, а также неверный пароль отклоняются без перезаписи текущего хранилища; файл не содержит секретных полей в открытом виде; восстановление в экземпляре Guardian не должно обходить обязательную MFA и должно использовать утверждённую проверку ключа или процедуру его повторной регистрации. Возможность дополнительного слоя шифрования и включение настроек MFA в файл фиксируются в проектном решении; универсальные форматы и обмен с другими менеджерами не поддерживаются.
- **Метод проверки:** Функциональный тест, инспекция формата.
- **Дополнительная информация:** CON-03, CON-05, CON-06; допущение A-08; связано с: REQ-SEC-001, REQ-REL-002.

- **ID:** REQ-FUNC-009
- **Название:** Блокировка и раскрытие секрета
- **Утверждение:** Система должна позволять пользователю немедленно заблокировать хранилище, скрывать пароли и заметки по умолчанию и требовать явного действия для раскрытия секрета.
- **Обоснование:** Сокращает вероятность случайного просмотра секретов.
- **Критерии приёмки:** После блокировки содержимое записей недоступно через интерфейс; секрет скрывается при уходе с экрана записи или блокировке хранилища.
- **Метод проверки:** Функциональный тест.
- **Дополнительная информация:** CON-04, CON-10; связано с: REQ-SEC-003.

- **ID:** REQ-FUNC-010
- **Название:** Обязательная двухфакторная аутентификация Guardian
- **Утверждение:** Система должна требовать для каждого разблокирования хранилища проверку мастер-пароля и независимого второго фактора; восстановление доступа допускается только через отдельный утверждённый процесс, не сводящийся к проверке одного мастер-пароля.
- **Обоснование:** Защищает доступ к самому Guardian дополнительным фактором; это отдельный сценарий от генерации TOTP-кодов для внешних сервисов.
- **Критерии приёмки:** При первоначальной настройке пользователь регистрирует USB-ключ FIDO2/WebAuthn; до успешной проверки мастер-пароля и ключа секретные записи недоступны; неверный или отсутствующий ключ не даёт разблокировать хранилище; утверждённая процедура восстановления после утраты ключа проверена до релиза; данные аутентификации защищены согласно проектному решению и не доступны в открытом виде.
- **Метод проверки:** Функциональный тест, негативный тест, инспекция.
- **Дополнительная информация:** CON-04; допущение A-06; тип второго фактора подтверждён; процедура восстановления после утраты ключа требует решения.
### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

Для релиза 1.0 не устанавливаются численные цели производительности и не создаются критерии приёмки по времени ответа. Отзывчивость проверяется в рамках обычного тестирования удобства использования; количественные цели могут быть согласованы отдельным изменением после получения пользовательской обратной связи (CON-10).

#### 3.3.2 Безопасность {#332-security}


- **ID:** REQ-SEC-001
- **Название:** Шифрование хранилища
- **Утверждение:** Система должна шифровать секретные поля и резервные копии с использованием актуальных, широко проверенных криптографических механизмов из поддерживаемой библиотеки; конкретные алгоритмы, параметры и схема управления ключами должны быть утверждены в проектной документации до релиза.
- **Обоснование:** Защита конфиденциальности данных при доступе к файлам устройства или копии.
- **Критерии приёмки:** Инспекция конфигурации и формата подтверждает шифрование; попытка чтения файла без ключа не раскрывает содержимое секретных полей; отсутствуют самописные криптографические примитивы без утверждённого исключения.
- **Метод проверки:** Анализ, инспекция.
- **Дополнительная информация:** CON-03, CON-08; параметры криптографии должны быть утверждены до выпуска.


- **ID:** REQ-SEC-002
- **Название:** Защита ключей и мастер-пароля
- **Утверждение:** Система не должна сохранять мастер-пароль или ключ расшифрования в открытом виде, а их производные значения должны храниться только в форме, одобренной анализом безопасности.
- **Обоснование:** Утечка файла приложения или хранилища не должна напрямую раскрывать секрет доступа.
- **Критерии приёмки:** В файлах, журналах, отчётах о сбоях и телеметрии отсутствуют мастер-пароль и ключ; параметры функции получения ключа документированы и проверены специалистом по безопасности.
- **Метод проверки:** Анализ, тестирование.
- **Дополнительная информация:** CON-03, CON-08; связано с: REQ-FUNC-001, REQ-OBS-001.


- **ID:** REQ-SEC-003
- **Название:** Блокировка хранилища
- **Утверждение:** Система должна позволять пользователю немедленно заблокировать хранилище и автоматически блокировать его при блокировке или выходе из сеанса Windows.
- **Обоснование:** Ограничивает доступ к открытому хранилищу, когда пользователь прекращает работу с сеансом.
- **Критерии приёмки:** Ручная блокировка немедленно делает записи недоступными; блокировка и выход из Windows приводят к блокировке Guardian; повторное открытие требует успешной проверки факторов входа. Интервал бездействия не задаётся как требование релиза 1.0.
- **Метод проверки:** Функциональный тест, интеграционный тест Windows.
- **Дополнительная информация:** CON-04, CON-10; связано с: REQ-FUNC-009, REQ-FUNC-010.

- **ID:** REQ-SEC-004
- **Название:** Очистка буфера обмена
- **Утверждение:** Если пользователь копирует пароль в буфер обмена, система должна очищать его при блокировке хранилища, если Windows позволяет управлять содержимым буфера.
- **Обоснование:** Сокращает период доступности секрета другим приложениям после завершения работы с хранилищем.
- **Критерии приёмки:** На поддерживаемой конфигурации копирование и очистка при блокировке проверяются интеграционным тестом; если Windows не позволяет очистить буфер, приложение предупреждает пользователя перед копированием и предоставляет явное действие очистки.
- **Метод проверки:** Интеграционный тест, демонстрация.
- **Дополнительная информация:** CON-01, CON-03; очистка зависит от разрешений Windows.

- **ID:** REQ-SEC-005
- **Название:** Проверка источника автозаполнения
- **Утверждение:** Система должна разрешать автозаполнение только при совпадении схемы, имени хоста и эффективного порта с источником записи; после перенаправления источник должен проверяться повторно.
- **Обоснование:** Защищает от фишинга и ошибочной передачи пароля.
- **Критерии приёмки:** Точные совпадения разрешены; похожие домены, другие порты и схемы, неизвестные домены и неоднозначные URL отклоняются; поддомены не считаются совпадением автоматически; негативные тесты подтверждают отказ во всех запрещённых случаях.
- **Метод проверки:** Негативные тесты, анализ.
- **Дополнительная информация:** CON-01, A-04; связано с: REQ-FUNC-006, REQ-INT-003.

#### 3.3.3 Надёжность {#333-reliability}


- **ID:** REQ-REL-001
- **Название:** Целостность при сбое
- **Утверждение:** Система должна сохранять изменения хранилища атомарно настолько, насколько это поддерживает выбранный формат, чтобы прерывание записи не приводило к незаметной потере или подмене ранее сохранённых данных.
- **Обоснование:** Повреждение хранилища может привести к невосстановимой потере секретов.
- **Критерии приёмки:** Инъекция прерывания во время сохранения не приводит к частично принятой записи; приложение сообщает о невозможности чтения и сохраняет исходный файл/копию для восстановления.
- **Метод проверки:** Тест отказоустойчивости.
- **Дополнительная информация:** CON-03, CON-05; связано с: REQ-FUNC-002, REQ-FUNC-008.


- **ID:** REQ-REL-002
- **Название:** Валидация резервной копии
- **Утверждение:** Система должна проверять целостность и формат резервной копии до восстановления и не должна заменять действующее хранилище непроверенными данными.
- **Обоснование:** Защищает от повреждённых, подменённых или несовместимых копий.
- **Критерии приёмки:** Повреждённые и неверно аутентифицированные копии отклоняются; исходное хранилище остаётся доступным.
- **Метод проверки:** Негативный тест.
- **Дополнительная информация:** CON-03, CON-05; связано с: REQ-FUNC-008.

#### 3.3.4 Доступность {#334-availability}

Для релиза 1.0 сетевой SLA и серверная доступность неприменимы: Guardian работает с локальным хранилищем автономно. Поддерживаемые выпуски Windows, браузеры автозаполнения и процедура восстановления должны быть утверждены до выпуска.


- **ID:** REQ-AVAIL-001
- **Название:** Доступность автономного использования
- **Утверждение:** После установки и создания хранилища пользователь должен иметь возможность выполнять локальные операции без подключения к сети.
- **Обоснование:** Пароли должны оставаться доступными при отсутствии сети, а продукт не должен зависеть от внешнего сервиса в релизе 1.0.
- **Критерии приёмки:** Создание, разблокировка, поиск, редактирование, генерация, TOTP и локальное резервное копирование проходят в изолированной сети; приложение не пытается отправлять содержимое хранилища во внешнюю сеть.
- **Метод проверки:** Тест в изолированной среде, анализ сетевого трафика.
- **Дополнительная информация:** CON-05; связано с: REQ-INT-002.

#### 3.3.5 Наблюдаемость {#335-observability}


- **ID:** REQ-OBS-001
- **Название:** Безопасная диагностика
- **Утверждение:** Система должна предоставлять локальные диагностические сообщения о сбоях и состоянии операций без паролей, мастер-пароля, TOTP-секретов, заметок, ключей и открытого содержимого записей; удалённая телеметрия отключена в релизе 1.0.
- **Обоснование:** Диагностика нужна для исправления проблем, но логи не должны стать каналом утечки.
- **Критерии приёмки:** Инспекция журналов и отчётов подтверждает отсутствие секретов; URL и логины маскируются либо не записываются; сетевой мониторинг не обнаруживает телеметрию; экспорт очищенного отчёта требует явного согласия пользователя.

- **Дополнительная информация:** CON-03, CON-05; связано с: REQ-SEC-002.

Критерии готовности релиза 1.0: нет открытых критических уязвимостей без принятия риска; проверены резервное копирование и восстановление; опубликованы инструкции установки, миграции и отката; владелец продукта и специалист по безопасности одобряют выпуск.

- **Дополнительная информация:** Связано с REQ-MAINT-001, REQ-SEC-001 и REQ-REL-002.

### 3.6 ИИ/МО {#36-aiml}

Guardian версии 1.0 не использует машинное обучение или генеративный ИИ. Эти разделы неприменимы; добавление ИИ в будущей версии потребует отдельного описания модели, данных, ограничителей, человеческого надзора и оценки этических рисков.

#### 3.6.1 Спецификация модели {#361-model-specification}

Не применимо: ML-модели в релизе 1.0 отсутствуют. Генератор паролей не является ML-моделью и должен использовать криптографически стойкий генератор случайных чисел.

#### 3.6.2 Управление данными {#362-data-management}

Для ML-обучения данные не собираются и не используются. Секреты хранилища не должны отправляться на обучение моделей или внешним аналитическим сервисам.

#### 3.6.3 Ограничители (Guardrails) {#363-guardrails}

Ограничители ML неприменимы. Безопасность действий и автозаполнения регулируется требованиями REQ-SEC-004, REQ-SEC-005 и REQ-FUNC-006.

#### 3.6.4 Этика {#364-ethics}

Оценка этичности ML неприменима, поскольку ML-компонентов нет. Интерфейс не должен вводить пользователя в заблуждение относительно того, куда передаётся секрет или какие гарантии предоставляет приложение.

#### 3.6.5 Human-in-the-Loop {#365-human-in-the-loop}

Решений, принимаемых ML, нет. Выбор записи для автозаполнения и раскрытие секрета требуют явного действия пользователя согласно функциональным требованиям.

#### 3.6.6 Жизненный цикл модели и операции {#366-model-lifecycle-and-operations}

Не применимо: модели не развёртываются, не переобучаются и не мониторятся.
